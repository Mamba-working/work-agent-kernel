# 跨进程 demo 迭代

本轮目标是在独立分支上运行实用 demo，并用少量测试捕获真实行为回归。保持 TypeScript 离线原型范围，未连接个人账号或真实模型。

## 分支与交付

| 分支 | 内容 |
| --- | --- |
| `demo/file-replay` | 追加式 JSONL 来源、独立回放演示、两个测试 |
| `demo/owner-decisions` | 持久模拟 Harness、本地 answer 命令、一个跨进程测试 |
| `demo/workbench` | 合并前两条分支的改动，再加组合演示和一个验收测试 |

集成分支保留两个功能提交，便于分别审查。main 不在这轮自动合并。

## 为什么做这些 demo

在基线 `0991910` 上，现有 EchoHarness 把运行回执保存在内存。第一次 `run --ticks 1` 提交后退出，第二个进程无法观察那个运行，事项保持 running 并报告错误。原来的 demo 重开内核时仍保留模拟 Harness 对象，因此没有覆盖这个边界。

新模拟 Harness 在独立的 provider.sqlite 保存接单请求、回执和报告。它立即产生合成报告，由下一次 Host tick 读取。这验证持久化，不模拟真实后台计算。

## 选定的结构

比较了把新适配器放进核心模块，以及把它们留在示例目录的两种方案。选择后者。Source 和 Harness 接口已足够，当前没有需要维护的新生产 API。

只有 `src/cli.ts` 增加了 `answer` 命令。Kernel、Host、领域类型和插件接口不变。来源示例负责 JSONL 格式，Harness 示例负责 provider 记录和合成报告，集成示例负责把它们装配起来。

同一事项后续输入曾触发重复提问。通过实际 CLI 复现后，在已有测试中加入“完成后收到补充”的步骤。模拟 Harness 现在从该事项的接单历史中读取最近一次已解决决定。没有为此增加重试框架或新的内核状态。

## 运行组合流程

```bash
npm ci --ignore-scripts
npm run check
npm run demo:loop
```

指定一个空目录可以保留可预测的产物位置。

```bash
npm run demo:loop -- --directory /tmp/my-work-agent-loop
```

驱动程序依次启动独立 CLI 进程：

1. 从文件接收最初请求并提交模拟执行。
2. 读取已保存的范围问题。
3. 在等待时追加一条重复消息、一条修订和一条补充。
4. 确认事项仍等待决定，补充已经排队。
5. 使用 answer 选择 `Loading only`。
6. 在原模拟 Session 提交后续执行。
7. 读取 ready 报告和实际 Markdown 草稿。
8. 再运行一次，确认没有新增工作或结果。

目录包含事件文件、内核数据库、provider 数据库、本地收件箱、草稿，以及每条 CLI 命令的 JSON 输出。草稿保留原始输入、修订和补充；这只是可审阅的输入汇编，不表示模型已经判断哪一版要求有效。

## 两条独立流程

- [文件回放](FILE-REPLAY.md)验证来源和游标。每个进程完成两个 tick，不声称恢复内存 EchoHarness 的活动运行。
- [个人决定](LOCAL-DECISION.md)验证 provider 持久化、回答和 Session 延续。

## 测试取舍

新增四个测试。分别覆盖正常追加回放、损坏的未读批次、个人决定流程、组合流程。每个测试都读取实际结果；没有断言私有调用顺序，也没有按测试数量或覆盖率扩充。

输入文件已消费的行必须保持不变。内容修改通过追加更高 revision 的事件表达。命令按顺序运行，一个 Host 拥有一个内核库。本轮不验证文件轮转、多进程竞争、真实认证或远端通知。
